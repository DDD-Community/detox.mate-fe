# Frontend Testing

중요한 핵심 로직의 회귀를 최소한의 테스트로 막는다. 테스트 계층을 채우거나 모든 사용자 흐름을 자동화하는 것을 목표로 삼지 않는다.

## 테스트 선택 기준

다음 세 조건을 **모두** 충족할 때만 대상으로 선택한다.

1. 오류가 사용자에게 중요한 피해를 만드는 **핵심 로직**인가?
2. 실제 분기·응답 순서·상태 상호작용 때문에 **회귀할 가능성**이 있는가?
3. 구현을 리팩터링해도 유지해야 하는 **지속적인 불변식**인가?

중요한 기능에 속한다는 이유만으로 모든 코드를 검사하지 않는다. 단순 검색·CRUD를 잠재적 위험만으로 복잡한 로직이라고 확대하지 않는다.

기본 제외 대상:

- HTTP URL·헤더·상태코드 등의 전송 계약 검사.
- 평범한 UI 렌더링·버튼 연결, 단순 CRUD·trim·filter.
- 생성 클라이언트·라이브러리·단순 helper를 다시 검사하는 테스트와 fixture 자체 검증.
- 내부 구현을 그대로 따라 쓰거나 동일 보장을 여러 계층에서 반복하는 테스트.

## 검증 범위 선택

- 로직의 입력·출력 또는 훅의 공개 액션·결과를 가장 작은 범위에서 검증한다.
- 핵심 로직이 컴포넌트와 본질적으로 결합되어 직접 검증이 부적절할 때만 RNTL을 선택한다. UI 통합 테스트를 기본값으로 두지 않는다.
- E2E는 다른 방식으로 검증하기 어려운 적격 로직에만 좁게 고려한다. 전체 흐름이나 대표 화면이라는 이유만으로 추가하지 않는다.
- Jest·RNTL·MSW 통합 인프라를 먼저 만들지 않는다. 선택된 로직을 현재 도구로 검증할 수 있는지부터 판단한다.
- 테스트 비율·커버리지 퍼센트·개수 목표와 고정된 계층별 필수 항목을 두지 않는다.

## 기존 테스트를 다룰 때

현재 구현·테스트·실행 설정을 먼저 읽는다. 과거 상태 라이브러리나 경로를 전제로 삼지 않는다.

불변식과 실제 검출할 버그를 기준으로 유지·축소·합침·제거 후보를 구분한다. 테스트 정리가 승인된 범위라면 낮은 가치나 중복 검사를 정리한다. 계획·리뷰 요청만 받은 경우 후보만 설명하고 코드를 삭제하지 않는다.

파일명이 HTTP라는 이유로 모든 테스트를 삭제하지 않는다. 인증 동시 갱신이나 실패 후 복구 같은 복잡한 로직은 세 조건으로 별도 판단한다. 전송 계약과 인증 로직의 불변식은 구분한다.

## 작성 규칙

- `describe`·`it`·`test`의 제목과 검증 의도를 설명하는 주석은 한글로 쓴다. 제목은 조건 → 행동 → 기대 결과가 드러나도록 작성한다. API·함수명·오류 코드·상태코드 등 고정 식별자와 테스트 실행기의 지시문은 원문을 유지한다.
- 조건 → 공개 행동 → 불변식으로 사례를 쓴다. 내부 ref·revision·캐시 구조와 구현을 복제한 기대값은 검사하지 않는다.
- 경합은 deferred Promise로 순서를 제어한다. 시간이 요구사항인 경우에만 타이머를 제어한다. 임의 sleep을 사용하지 않는다.
- 필요한 최소 fixture를 쓰고 테스트별 상태·모킹·타이머·렌더를 정리한다. 실제 네트워크나 실행 순서에 의존하지 않는다.
- 중복 쓰기 방지의 관찰값으로 쓰기 횟수를 확인할 수 있다. 모든 조회 횟수나 호출 순서를 고정하는 계약 검사는 추가하지 않는다.
- 공개 결과를 직접 검증할 수 있으면 화면·모킹 서버까지 범위를 넓히지 않는다. 같은 불변식의 겹치는 하위 사례는 선택하거나 합친다.

## 선택 사례

아래는 판단 예시이며 모두 추가하라는 목록이 아니다.

| 선택할 불변식                                                          | 핵심 위험·복잡성                             | 최소 검증                                        |
| ---------------------------------------------------------------------- | -------------------------------------------- | ------------------------------------------------ |
| 오래된 조회가 확정된 삭제를 복원하지 않는다                            | 비동기 완료 순서가 삭제 결과를 덮어씀        | 조회 보류 → 삭제 완료 → 옛 조회 완료 → 삭제 유지 |
| 이전 사용자 작업이 새 사용자 데이터를 오염시키지 않는다                | 사용자 전환과 비동기 응답이 겹쳐 데이터 노출 | 전환 후 옛 응답 완료 → 이전 데이터 미노출        |
| 중복 액션은 추가 쓰기를 만들지 않는다                                  | 연속 액션과 처리 상태가 겹쳐 중복 변경       | 첫 쓰기 보류 → 연속 액션 → 쓰기 한 번            |
| 변경 실패 후 재시도 가능하며 확정 변경은 재조회 실패로 취소되지 않는다 | 쓰기·읽기 실패 경로가 잠금이나 결과를 훼손   | 필요한 오류 경로만 골라 복구 또는 확정 결과 유지 |

단순 이름 필터, 버튼 콜백 연결, DELETE 경로·204 처리, fixture 개수 검사는 자동 대상이 아니다. focus/blur 검사만으로 실제 사용자 전환의 데이터 격리가 증명되었다고 하지 않는다.

## 결과 보고

선택·생략·정리한 이유와 보호하는 불변식을 짧게 설명한다. 저장소의 적절한 검사만 실행하고 실제 실행 결과·미실행 항목·검증 한계를 구분한다. 통과 개수만으로 안정성을 선언하지 않는다.

계획 문서나 작업 체크리스트 생성을 강제하지 않는다. 필요한 작업 메모는 Git 제외 `.local/`에만 둔다. 이 스킬은 로컬 문서 없이도 적용할 수 있어야 한다.

[Testing Implementation Details](https://kentcdodds.com/blog/testing-implementation-details)는 리팩터링 내성의 참고다. [Testing Trophy](https://kentcdodds.com/blog/the-testing-trophy-and-testing-classifications)는 범위·비용을 판단하는 보조 모델이며 계층 의무가 아니다. 매 테스트마다 자료 조사를 요구하지 않으며, 위 사용자 정책을 우선한다.
