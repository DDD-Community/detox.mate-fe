# Amplitude 분석 로그 연동 계획

## 목적

이 문서는 디톡스메이트 FE에 Amplitude 로그를 연동하기 위한 진행 순서, 분석 목적, 로그 설계 기준, 최종 산출물을 정리한다.

이번 작업은 다음 순서대로 진행한다.

1. SDK 연결
2. 공통 모듈 구현
3. 전체 로그 스키마 설계
4. 하나씩 적용

## 분석 목적

FE 로그의 목적은 사용자가 어디서 이탈하는지, 어떤 조건의 유저가 계속 사용하는지, 핵심 행동까지 도달하는지를 분석하기 위함이다.

주요 분석 방식은 다음 3가지다.

| 분석           | 목적                                           | 주 확인 위치 |
| -------------- | ---------------------------------------------- | ------------ |
| 성공 지표 분석 | 가설 검증 여부 확인                            | 서버 DB      |
| 코호트 분석    | 리텐션 검증, 며칠째 이탈하는지 확인            | Amplitude    |
| 퍼널 분석      | 목표 행동까지의 단계별 전환율과 이탈 지점 확인 | Amplitude    |

## 타겟과 가설

### 타겟

스크린타임 제한이나 터닝 같은 스마트폰 제한 앱을 사용해봤지만 사용 시간 감축에 실패했고, 열품타, 투두메이트, 챌린저스, 루틴 인증방처럼 타인에게 보이는 인증, 기록, 응원이 있을 때 목표를 더 잘 지속하는 사람.

### 가정

친구에게 스크린타임을 인증해야 하면 수치심과 책임감 때문에 실제 사용 시간을 줄일 것이다.

### 가설

타겟 유저가 지인과 그룹을 만들고 인증을 시작했으면, 2주 내 평균 스크린타임이 감소할 것이다.

## 분석 설계

### 1. 성공 지표 분석

성공 지표 분석은 서버 DB를 기준으로 확인한다. FE 로그는 이 지표의 원인을 해석하기 위한 보조 신호로 사용한다.

#### 효과성 분석

| 지표                   | 계산 기준                                                     |
| ---------------------- | ------------------------------------------------------------- |
| 평균 스크린타임 감소율 | 2주간 스크린타임 평균 사용 시간 / 처음에 설정한 스크린타임 값 |
| 스크린타임 목표 달성율 | 2주간 스크린타임 평균 사용 시간 / 목표 시간                   |

#### 원인 분석

| 지표                       | 의미                        |
| -------------------------- | --------------------------- |
| 그룹 내 상호작용 수        | 댓글 수, 찌르기 수, 반응 수 |
| 그룹 스트릭 연속 유지 날짜 | 그룹 단위 인증 지속성       |

### 2. 코호트 분석

코호트는 공통된 특성이나 경험을 공유하는 사람들의 집단이다.

코호트 분석의 목적은 다음과 같다.

- 사용자가 시간이 지나도 계속 남는지 확인한다.
- 제품 변경 이후 가입자 또는 시작자의 잔존율이 이전보다 좋아졌는지 확인한다.
- 가입 후 1일 차, 7일 차, 인증 시작 후 특정 시점 등 어디서 이탈하는지 찾는다.

확인할 지표는 다음과 같다.

- 유저들이 며칠 동안 사용하는가?
- 며칠째쯤에 재사용 비율이 떨어지는가?
- 방장 여부에 따라서 리텐션이 어떻게 달라지는가?
- 알림 허용 여부에 따라서 리텐션이 어떻게 달라지는가?

보는 방법:

- Amplitude에서 확인한다.
- 방장 여부는 `group_role` user property 기준으로 본다.
- 알림 허용 여부는 `push_notification_enabled` user property 기준으로 본다.

### 3. 퍼널 분석

퍼널 분석은 사용자가 목표 행동까지 가는 단계별 전환율과 이탈 지점을 보는 분석이다.

우선 확인할 퍼널은 다음과 같다.

#### 가입 → 공유 퍼널

목적: 앱에 들어온 유저가 그룹을 만들고 공유 버튼까지 도달하는지 확인한다.

| 단계           | 이벤트 예시                   |
| -------------- | ----------------------------- |
| 앱 시작        | `App Opened`                  |
| 인트로 확인    | `Onboarding Viewed`           |
| 그룹 생성 완료 | `Group Created`               |
| 공유 버튼 클릭 | `Invite Share Button Clicked` |

#### 가입 후 목표 설정 퍼널

목적: 홈에 들어온 유저가 목표 설정과 목표 인증까지 도달하는지 확인한다.

| 단계                | 이벤트 예시              | 주요 property           |
| ------------------- | ------------------------ | ----------------------- |
| 홈 진입             | `{Page Name} Viewed`     | `page_name = FeedHome`  |
| 목표 설정 화면 진입 | `Goal Setup Viewed`      | `page_name = GoalSetup` |
| 시간 설정 완료      | `Goal Time Set`          | -                       |
| 인증 완료           | `Verification Completed` | -                       |

이 퍼널은 방장 여부에 따라 구분해서 본다.

- 방장: `group_role = OWNER`
- 멤버: `group_role = MEMBER`

## 진행 순서

### 1. SDK 연결

상태: 완료

Amplitude SDK를 프로젝트에 연결한다.

확인할 내용은 다음과 같다.

- React Native/Expo 환경에서 사용할 SDK를 결정한다. 완료
- API key를 dev/prod 환경별로 분리한다. 완료
- 앱 시작 시점에 SDK를 초기화한다. 완료
- 인증 전 익명 사용자와 인증 후 식별 사용자의 연결 방식을 확인한다. 다음 단계

사용 SDK는 Amplitude의 최신 React Native SDK다.

- `@amplitude/analytics-react-native`
- `@react-native-async-storage/async-storage`

구현 위치는 다음과 같다.

| 항목            | 위치                             |
| --------------- | -------------------------------- |
| 패키지 설치     | `package.json`, `pnpm-lock.yaml` |
| API key 주입    | `app.config.ts`                  |
| 환경값 검증     | `src/config/env.ts`              |
| 초기화 함수     | `src/lib/analytics.ts`           |
| 앱 시작 시 호출 | `app/_layout.tsx`                |

참고 문서:

- [Amplitude React Native SDK](https://amplitude.com/docs/sdks/analytics/react-native/react-native-sdk)
- [Amplitude tracking plan](https://amplitude.com/docs/data/create-tracking-plan)

### 2. 공통 모듈 구현

상태: 완료

SDK를 직접 화면에서 사용하지 않고 공통 모듈을 통해 사용한다.

공통 모듈의 목적은 다음과 같다.

- `track` 호출 방식을 통일한다.
- 화면/버튼/핵심 이벤트 property 이름을 통일한다.
- 개인정보와 민감 정보가 들어가지 않도록 진입점을 제한한다.
- 이후 Amplitude 외 다른 분석 도구를 붙이더라도 화면 코드를 크게 바꾸지 않도록 한다.

예상 API는 다음 형태를 기준으로 한다.

```ts
initAnalytics();
setAnalyticsUserId(userId);
setAnalyticsUserProperties(properties);
trackEvent(eventName, properties);
trackScreenView(eventName, pageName, properties);
trackButtonClick(eventName, pageName, buttonName, properties);
```

현재 `src/lib/analytics.ts`에 공통 모듈 구현이 완료되어 있다. 화면별 실제 로그 적용은 다음 단계에서 진행한다.

### 3. 전체 로그 스키마 설계

공통 모듈에 넣을 기본 property와 이벤트별 property를 설계한다.

#### 공통 property

| property      | 설명                                         | 필수 여부             |
| ------------- | -------------------------------------------- | --------------------- |
| `event_type`  | `screen_view`, `button_click`                | 화면/버튼 이벤트 필수 |
| `page_name`   | 이벤트가 발생한 화면 이름                    | 화면/버튼 이벤트 필수 |
| `button_name` | 실제 버튼 텍스트 또는 아이콘 역할명          | 버튼 이벤트 필수      |
| `entry_point` | 같은 행동이 여러 진입점에서 발생할 때만 사용 | 필요 시               |

#### 사용자 식별

사용자 식별은 공통 모듈에서 관리한다.

| 항목    | 기준                                                                      |
| ------- | ------------------------------------------------------------------------- |
| 인증 전 | Amplitude device id 또는 익명 식별 흐름 사용                              |
| 인증 후 | 서버의 안정적인 내부 user id를 `setUserId`로 설정                         |
| 금지    | 이름, 닉네임, 전화번호, 이메일, 원본 초대코드 등 직접 식별 가능 정보 전송 |

#### 이벤트별 property

| 이벤트 성격 | 추가 property                               |
| ----------- | ------------------------------------------- |
| 페이지 뷰   | `event_type`, `page_name`                   |
| 버튼 클릭   | `event_type`, `page_name`, `button_name`    |
| 그룹 참여   | `entry_point`                               |
| 목표 설정   | `mode`                                      |
| 인증        | `verify_mode`, `goal_achieved`              |
| 푸시        | `next_enabled`, `push_notification_enabled` |

### 4. 하나씩 적용

모든 페이지 뷰와 모든 버튼 클릭에 로그를 붙인다.

적용 순서는 다음을 기준으로 한다.

1. 앱 진입, 로그인, 온보딩
2. 그룹 생성
3. 초대코드 참여
4. 목표 설정
5. 인증 플로우
6. 피드, 반응, 댓글, 찌르기
7. 마이페이지, 설정, 알림
8. 푸시알림

주요 적용 대상 파일은 다음 영역이다.

- `app/**`
- `src/screens/auth/**`
- `src/screens/group/**`
- `src/screens/feed/**`
- `src/screens/notification/**`

AI를 이용해 일괄 적용하되, 다음 조건을 확인한다.

- 화면 진입 로그가 중복으로 찍히지 않는다.
- 버튼 클릭 로그가 실제 사용자 액션 시점에 찍힌다.
- API 성공/실패 결과가 필요한 이벤트는 결과를 구분한다.
- 개인정보와 민감 정보가 property에 들어가지 않는다.
- dev/prod 구분은 Amplitude API key와 프로젝트 분리로 처리한다.

## FE 로그 주의사항

FE 로그는 다음 원칙을 지킨다.

- 모든 버튼 클릭, 페이지 뷰에 로그를 붙인다.
- 유저 식별 정보를 공통 모듈에서 관리한다.
- 공통 스키마로 기록한다.
- 개인정보와 민감 정보를 포함하지 않는다.
- dev와 prod를 구분한다.
- 성공 지표의 최종 판정은 서버 DB 기준으로 보고, FE 로그는 퍼널/코호트/행동 원인 분석에 사용한다.

## 최종 결과

작업이 완료되면 다음 결과물이 남아야 한다.

| 결과물             | 설명                                                                              |
| ------------------ | --------------------------------------------------------------------------------- |
| SDK 연결           | Amplitude SDK가 dev/prod 환경별 설정으로 초기화됨                                 |
| 공통 모듈          | 화면 코드에서 직접 SDK를 호출하지 않고 공통 API로 로그를 남김                     |
| 로그 스키마        | 공통 property, 이벤트명, 이벤트별 property 기준이 문서화됨                        |
| 페이지 뷰 로그     | 주요 화면 진입 시 고유한 `{Page Name} Viewed` 로그가 남음                         |
| 버튼 클릭 로그     | 주요 버튼 클릭 시 고유한 `{Page Name} {Action} Clicked` 로그가 남음               |
| 핵심 퍼널 이벤트   | 그룹 생성, 그룹 참여, 목표 설정, 인증 완료 흐름을 Amplitude에서 퍼널로 볼 수 있음 |
| 코호트 기준 이벤트 | 첫 그룹 생성, 첫 그룹 참여, 첫 인증 완료 기준으로 리텐션을 볼 수 있음             |
| 개인정보 보호 기준 | 이름, 닉네임, 이메일, 전화번호, 원본 초대코드 등 민감 정보가 로그에 포함되지 않음 |

최종적으로 Amplitude에서 다음 질문에 답할 수 있어야 한다.

- 앱에 들어온 유저가 그룹 생성 또는 그룹 참여까지 얼마나 도달하는가?
- 그룹을 만든 유저가 공유 버튼까지 얼마나 도달하는가?
- 초대코드로 들어온 유저가 목표 설정과 첫 인증까지 얼마나 도달하는가?
- 첫 인증을 완료한 유저는 며칠 동안 다시 사용하는가?
- 상호작용이 많은 그룹의 스크린타임 감소율이 더 좋은가?
- 푸시알림 허용 여부가 핵심 행동 전환에 영향을 주는가?
